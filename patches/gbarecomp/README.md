# Local patches to gbarecomp

Fixes we need in gbarecomp before upstream has them. They form a series: `scripts/apply-patches.sh` applies every `*.patch` here in name order, each on top of the pinned commit plus the patches before it, to the submodule's working tree. `scripts/setup.sh` runs it, and so does every build script before it builds anything. We never commit inside the submodule: the repository records only the pinned gbarecomp commit. After setup, `git status` shows `gbarecomp (modified content)`; that is the applied series.

These patches change gbarecomp and contain excerpts of its source, so they are distributed under the same terms, for noncommercial purposes only.

The native build and gbarecomp's own tests pass on macOS arm64 without any patch at the pin (`5e89943528aee7bc1c399bdbd035364a4b41dd10`). `0001` is for running the browser bundle; `0002` makes one of gbarecomp's browser unit tests reliable on a busy Linux CI runner; `0003` and `0004` fix the runtime's IRQ call-return leak and its end-of-run IRQ watchdog ([Phase 2 diagnosis](../../docs/research/phase2-diagnosis.md), §1.1 and §1.2), without which the game aborts after about 2,700 frames; `0005` adds the capture that compares gbarecomp with mGBA; `0006` lets game code pick, at each dispatch, the compiled corpus of the code image resident in RAM, for the two images that share IWRAM ([ADR 0001](../../docs/adr/0001-port-via-static-recompilation.md), decision 2); `0011` and `0012` bring two CPU timing rules in line with mGBA, the GamePak prefetch reset on a PC write and the cycles of IRQ entry, without which every race leaves lockstep with mGBA ([phase2-race-lockstep.md](../../docs/research/phase2-race-lockstep.md)). Numbers 0007-0010 are proposed for other tasks ([phase2-plan.md](../../docs/phase2-plan.md), "Patch queue") and assigned when they land.

gbarecomp's nested submodule `external/arm-recomp-core` has a series of its own, [`patches/arm-recomp-core/`](../arm-recomp-core/README.md), applied by the same script after this one ("The nested series" below). `0011` needs its `0001`.

## How the series is applied

```sh
scripts/apply-patches.sh            # make gbarecomp/ the pin plus the series (both series)
scripts/apply-patches.sh --check    # exit 0 if it is, 1 if not; changes nothing in gbarecomp/
scripts/apply-patches.sh --reverse  # restore the pin
scripts/apply-patches.sh --diff     # what gbarecomp/ has on top of the pin plus the series
scripts/apply-patches.sh --series arm-recomp-core --check   # one series only
```

Everything in this section holds for each series separately, the nested one included ("The nested series" below); the commands act on both unless `--series` names one.

The script applies the series in order to a scratch index on top of the pin, never to the working tree directly, and then writes only the files whose content differs from what is there. So a patch may change lines that an earlier patch changed, or lines next to them. (PR #5's version judged each patch on its own against the fully patched tree. With two patches whose hunks overlap each other's context, the earlier one neither applied nor reverted there, so every build after the first stopped. `tests/tooling/apply-patches-test.sh` shows that case.)

Before it writes anything, the script checks that the current tree is a state it can explain:

- the pin;
- the pin plus a leading part of the series (several new patches pulled at once);
- the pin plus the series with one patch left out (an A/B build, below);
- what it last wrote, according to its stamp, `build/gbarecomp-patches/stamp`, including a run that stopped halfway;
- the series of one of the last 100 commits reachable from `HEAD` that changed `patches/gbarecomp/`. A series that only another branch has is not found this way.

From any of these it switches straight to the pin plus the current series (or the A/B variant asked for), removing files that an earlier series added and that the current one does not. Anything else is a hand edit, or a nested submodule that is not at the commit gbarecomp pins (for `external/arm-recomp-core`, whose content its own series manages, only its commit counts here): the script stops before writing anything in that tree, lists the files that differ from the closest known state, and says how to keep or discard them. The build scripts stop the same way, since they all run it first. The gbarecomp series is handled first: when it switches and the nested one then stops, run the script again once the cause is fixed; it finds the gbarecomp tree in place.

The pin is the commit checked out in `gbarecomp/`. When the repository records another one (`git ls-files -s gbarecomp`, for example after a pull that moved the pin without `git submodule update`), `--check` fails and the other modes warn.

The stamp records the pin, a hash of the series and the resulting tree. When the stamps of both series match, the build scripts' check takes about 0.4 s on the M4 Pro and changes nothing. `build/gbarecomp-patches/` also holds the scratch git objects the script creates, so that it adds nothing to the submodule's repository, and the build lock (below). Deleting the directory loses nothing, with one exception: the script recognizes the tree from the other states listed above, but not the tree of an A/B build that left two or more patches out. Every build then stops as for a hand edit, until `scripts/apply-patches.sh` is run with the same `--without` options; the message says so. Do not save that tree with `--write-patch`: the patch would undo the patches left out. The script writes files only in the submodule's working tree, and only to switch between known states.

## The nested series

`patches/arm-recomp-core/` is a second series, for gbarecomp's nested submodule `gbarecomp/external/arm-recomp-core` ([its README](../arm-recomp-core/README.md)). The script runs once per series, gbarecomp's first, with the same checks and the same states it can explain; what differs:

- Its pin is the commit checked out in `gbarecomp/external/arm-recomp-core`. When gbarecomp's index records another one (after `git -C gbarecomp checkout NEW` without `git -C gbarecomp submodule update`), `--check` fails and the other modes warn, as for gbarecomp itself. The gbarecomp series checks only that commit; the nested tree's content is this series' business.
- Its patches are written against arm-recomp-core, with paths relative to it (`a/profiles/armv4t_gba/...`). `--write-patch patches/arm-recomp-core/NNNN-name.patch` saves a change made in `gbarecomp/external/arm-recomp-core/` (the file's directory picks the series; for a file elsewhere, `--series arm-recomp-core` does).
- `--without` names its patches with the series' name: `--without arm-recomp-core/0001` (or the patch's path). A plain number is a patch of `patches/gbarecomp/`. The A/B directory gets the name with `-` for `/`: `build/without-0011-arm-recomp-core-0001/`.
- `--diff` prints the changes of both series as one patch relative to `gbarecomp/`, the nested files under `external/arm-recomp-core/`, so `scripts/apply-patches.sh --diff | git -C gbarecomp apply -R` discards hand edits in both (`git apply` writes into the nested repository's files).
- Its stamp and scratch objects are in `build/gbarecomp-patches/arm-recomp-core/`. The history it searches is that of `patches/arm-recomp-core/`.
- With no patch in it, it checks that the nested tree is its pin, as the script did before this series existed.

A fix may need both repositories, as the prefetch reset does (`0011` here, `0001` there). Each patch then says, in its header, which patch of the other series it needs. The script does not know about such pairs: an A/B build must leave out both, or neither.

**Branches older than this series.** The scripts of a branch that predates `patches/arm-recomp-core/` refuse any change in the nested tree: once this series is applied, `scripts/apply-patches.sh --check` there prints `NO: nested submodules of gbarecomp are not at their pinned commit or have local changes: external/arm-recomp-core`, and every build script stops with the same message. Before checking out such a branch, run `scripts/apply-patches.sh --reverse --series arm-recomp-core` here: it restores the nested pin and leaves gbarecomp's series, which the older script recognizes from the stamp. If the older branch is already checked out, `git -C gbarecomp/external/arm-recomp-core checkout -- .` does the same, but it also discards any hand edit in the nested tree: save one first with `--write-patch` on a branch that has this series. Back on a branch with the series, its next build applies the nested series again.

## A/B builds: leaving patches out

To build without some patches, for example to show that a bug comes back without its fix, pass `--without` to any build script:

```sh
scripts/build-native.sh --without 0003           # into build/without-0003/native
scripts/test-engine.sh --without 0003 -R some_test
scripts/smoke-test.sh --native-only --without 0001
MRA_WITHOUT_PATCHES="0003 0007" scripts/regen.sh  # the same through the environment
scripts/repro-test.sh --without 0011 --without arm-recomp-core/0001 --expect-failure prefetch1
                                                  # a patch of the nested series too
```

`NAME` is a patch's number or file name, or `arm-recomp-core/NUMBER` for the nested series, and `--without` can be repeated. The script applies the series without those patches, and every output of the build goes under `build/without-NAME/` (for several, `build/without-0003-0007/`): the gbarecomp tools, the generated code, the native and web builds, logs and saves. Apart from `build/gbarecomp-patches/`, an A/B build never writes the normal `build/` or `generated/`. The next normal build switches the submodule back to the full series; only the files that differ are written, so the normal build recompiles only what depends on them. `scripts/apply-patches.sh --without NAME` switches the tree without building, and `scripts/serve-web.sh --without NAME` serves the bundle that `scripts/build-web.sh --without NAME` built.

A patch that stacks on one left out does not apply without it. The script then stops before writing anything and names both, for example `0009-....patch does not apply without 0007, which it stacks on`: leave it out too (`--without 0007 --without 0009`).

**One build at a time per checkout.** An A/B build switches `gbarecomp/` itself, the tree the normal build compiles too. So the build scripts, and `apply-patches.sh` in every mode but `--check` and `--diff`, hold a lock, `build/gbarecomp-patches/lock`, for their whole run. One started meanwhile waits, and says what it is waiting for. A lock left by a script killed with `SIGKILL` is removed by the next run, with a warning. After an A/B build, `gbarecomp/` keeps the variant until the next normal build script or `apply-patches.sh` run, as the build says at the end. A build by hand (`cmake --build`, `docs/toolchain.md`) takes no lock and compiles whatever is in place: run `scripts/apply-patches.sh` first, and not while a script runs. To build two series at the same time, use a second git worktree.

Example: `scripts/smoke-test.sh --native-only --without 0001` fails with `internal: value flag --state-dir is missing from kCliValueFlags`, the bug 0001 fixes, and the next `scripts/smoke-test.sh` restores 0001 and passes.

## Adding a patch

1. Make the change in `gbarecomp/` (or in `gbarecomp/external/arm-recomp-core/`, for the nested series: then use `patches/arm-recomp-core/` below).
2. Save it as the next patch: `scripts/apply-patches.sh --write-patch patches/gbarecomp/NNNN-short-name.patch`, numbered after the last one (and after any number another task has reserved, phase2-plan.md "Patch queue"). It writes the difference between `gbarecomp/` and the pin plus the existing series. The build scripts refuse to build while `gbarecomp/` has an edit that no patch holds, so save before each build. After further edits, run the same command again: it rewrites the file and keeps its header, the blank lines under it included.
3. Build and test the change.
4. Above the first `diff --git` line, which `git apply` ignores, write the header: what the patch fixes, why, and how it was tested, ready for upstream.
5. Add a row to the table above.
6. `scripts/apply-patches.sh --check` reports the series as applied.

## Changing a patch in the middle of the series

`--write-patch FILE` writes FILE against the patches that come before it in the series, so that it applies at its place: for `0007-x.patch`, the pin plus 0001 to 0006. The patches after it are first taken back out of the tree (reverse-applied in a scratch index), so that their changes stay out of FILE and they still apply on top of it. The script then checks that the series gives the current tree. With nothing changed, it leaves a patch it wrote byte for byte as it was.

When the edit overlaps a later patch (it changes that patch's lines or the three lines around them, as happens when the later patch stacks on FILE), the script cannot tell which of the two the edit belongs to. It stops, names both patches and writes nothing. Take the later patch out first. For example, with 0009 stacked on 0007:

1. `scripts/apply-patches.sh --without 0009`, then make the edit in `gbarecomp/`. If it is already made on the full series, save it with `scripts/apply-patches.sh --diff > build/edit.diff` and undo it with `git -C gbarecomp apply -R ../build/edit.diff` first, then make it again after the switch.
2. `scripts/apply-patches.sh --write-patch patches/gbarecomp/0007-x.patch --without 0009`.
3. `scripts/apply-patches.sh`. If 0009 still applies, that is all. Otherwise it stops at 0009, and nothing is written: `git -C gbarecomp apply --reject ../patches/gbarecomp/0009-y.patch` applies the hunks that still fit and leaves the others in `.rej` files. Make those changes by hand, delete the `.rej` files, and run `scripts/apply-patches.sh --write-patch patches/gbarecomp/0009-y.patch`.

`tests/tooling/apply-patches-test.sh` runs these steps on its toy series.

## Moving the pin

1. `scripts/apply-patches.sh --reverse` (both series: `git submodule update` below would not move a nested submodule with local changes).
2. Move the submodule and record it: `git -C gbarecomp checkout NEW`, `git -C gbarecomp submodule update -- external/arm-recomp-core` (in case NEW moves it), then `git add gbarecomp`. Until the new commit is recorded, the script warns that `gbarecomp/` is not at the commit the repository records, and `--check` fails.
3. Run `scripts/apply-patches.sh`. It stops at the first patch that no longer applies on the new pin, before writing anything in that tree: refresh it, or drop it if upstream fixed the problem. If NEW moved arm-recomp-core, the nested series is applied on its new commit, and the same holds for its patches.
